# 解說頁的寫法

`explain` 和 `checkpoint` 的 HTML 頁共用這份。`<P>` 是這個資料夾（plugin 根目錄的 `pages/`）。頁面是一次性的：放 scratchpad，不進 repo。

## 來源

讀者靠這頁理解系統，一句錯的說明會讓他帶著錯的印象去改程式。

- 先讀 CLAUDE.md / AGENTS.md，找出需求、計畫、進度、票、決定紀錄（ADR、決策紀錄或偏差紀錄）、名詞表放在哪裡。repo 沒有其中某一樣時，從 git log、PR、README 和程式碼裡的註解取，並在頁面上說明這部分沒有文件可引。
- 「現在怎麼運作」以**程式碼**為準，每句附 `檔案:行`。
- 「為什麼這樣做」引文件原文：需求、計畫、ADR、偏差紀錄、票的 Comments、commit，附章節或 hash。
- 文件說的和程式做的不一樣：不在正文裡挑一邊講，另列〈文件和程式對不上〉，兩邊的來源都附。
- 找不到來源的句子標 `推斷`（`tag guess`），寫出根據什麼推的。
- 決定附**決定者**：使用者定、使用者同意（agent 提議）、Agent 定、不明（當時沒記）。repo 有標就照標，沒標的照原文判斷，判斷不了寫不明。

## 圖

用 Mermaid，只用 `flowchart`、`sequenceDiagram`、`stateDiagram-v2`、`classDiagram`、`erDiagram` 這幾種。

- 有先後順序的過程（誰先呼叫誰、等多久、重試幾次）用 `sequenceDiagram`；`flowchart` 畫結構和分岔。
- 一張圖 ≤ 15 個節點；更大就拆成總圖加分圖。
- 節點標籤加雙引號，寫使用者看得懂的話；程式名稱放括號裡，例如 `A["送下載（submit_job）"]`。
- 每張圖下面一兩句說這張圖在講什麼、從哪裡讀起。

圖寫在 `<pre class="mermaid">` 裡；Mermaid 和縮放由〈組頁〉放上。

## 組頁

頁面寫成 `<名稱>-src.html`，再組成 `<名稱>.html`：

```
python <P>/scripts/build.py <名稱>-src.html
```

`build.py` 在 `<head>` 內嵌樣式，在頁尾放上從 CDN 載入 Mermaid 和 Panzoom 的 `<script>`、內嵌縮放拖動的程式，再用本機的 Chrome 或 Edge 逐張確認圖畫得出來，並在寬螢幕和手機寬各量一次水平溢出；退出碼和訊息的意義寫在它開頭。它說有水平溢出時不產出：照它列的元素，讓那段文字換行，或把寬的表格、程式碼放進自己橫向捲動的容器。原始頁自己不載入任何外部資源（CDN 的 script、樣式、字型、圖片），也不重新定義配色變數，否則它拒絕產出。要改頁面就改 `-src.html` 再重組。打開組好的頁要有網路。

## 外觀

樣式由〈組頁〉內嵌（`scripts/tokens.css`、`scripts/page.css`）：原始頁只寫內容，整頁包在 `<main>` 裡，用下表的元件。版面是一般文章：70ch 文字欄、標題和留白分段，表格只用在真正逐列比較的地方。

| 寫法 | 用在 |
| --- | --- |
| `<p class="meta">` | 頁首的日期、範圍 |
| `<div class="lede">` | 結論或一段話摘要，一頁一個 |
| `<span class="src">` | 接在句子後面的來源；〔〕由樣式加 |
| `<span class="tag">` | 決定者這類分類；推斷寫 `class="tag guess"` |
| `<span class="good">`、`bad`、`warn` | 狀態：過了、沒過、有但書 |
| `<div class="q">`，裡面 `<p class="rec">` | 要讀者確認的一題，和它的建議 |
| `<details>` | 條數多的清單、想看才看的細節 |
| `<p class="cap">` | 圖下面的說明 |
| `<td class="n">` | 題號、數字欄 |
| `<footer>` | 核對紀錄 |

這些不夠用時，在原始頁自己的 `<style>` 補 class，顏色和字體照 [TOKENS.md](TOKENS.md) 取變數；變數本身不重新定義。

## 寫法

讀者是 repo 的主人，常常不是這個領域的專家。

- 頁面用使用者對話的語言。
- 先講效果，再講機制：「你按下確認之後，系統會…」，再說哪個模組做的。
- 名詞用 repo 名詞表的詞。名詞表的詞，和讀者不一定認得的技術詞（套件、工具、錯誤碼、測試種類），第一次出現都附一句白話解釋。
- 變化寫成「以前…，現在…」。
- commit 在正文裡用它代表的時間點稱呼（「M0 驗收時的 main」「今天的 main」），hash 放進來源標籤。
- 一個列表項目講一件事；幾件小事就拆成子列表。
- 要讀者追認、歸類或略過的清單逐條列全，條數多就放進 `<details>`，`<summary>` 寫條數。讀者只能對看得到的條目負責。

## 交出前

1. **核對**：把整頁和頁上引到的來源交給一個沒看過你結論的子代理（Agent 工具，`model: "opus"`），回報兩種句子：附了來源卻和來源對不上的；講了事實、預估或因果，卻沒附來源也沒標 `推斷` 的。改掉、補來源，或改標 `推斷`。頁尾寫核對紀錄：核對幾句、改了幾句、改標 `推斷` 幾句。
2. **渲染**：`build.py` 退出碼 0 就算過（有圖時它印出「N 張圖都畫出來了」）。它說找不到 Chrome 或 Edge 時，先照第 3 步開 server，再用瀏覽器自動化工具（下面以 playwright 為例）打開那個網址：
   - 視窗寬 1440 和 390 各看一次：`document.documentElement.scrollWidth` 不大於 `innerWidth`。
   - 確認每張圖都畫成 svg、圖裡掛上了縮放按鈕列（`.dz-bar`）、畫面文字（`document.body.innerText`）沒有 `Syntax error`。查畫面文字，不查原始碼：圖的原始碼和頁上的說明都可能含這個字串。
   - 截圖的檔名用 scratchpad 的完整路徑。
   - 檢查完關掉 playwright 的頁；它在工作目錄建了 `.playwright-mcp/` 的話刪掉。
3. **交給使用者**：照 [HANDOFF.md](HANDOFF.md)。

完成條件：核對回報的每一句都處理了，頁尾有核對紀錄；每張圖都畫得出來、兩種寬度都沒有水平捲軸（`build.py` 退出碼 0，或 playwright 退路檢查過）；`HANDOFF.md` 的完成條件成立。

## 交出後的對話

- 回答追問，附來源。問到某個功能或機制怎麼運作，先從它的入口追到終點（經過哪些模組、在哪裡分岔、出錯時怎麼辦），每一步附 `檔案:行`，再答。
- 問一次要不要做**理解檢查**：出 2–3 題「如果 X 發生，系統會怎樣」，答錯的地方再講一次。
