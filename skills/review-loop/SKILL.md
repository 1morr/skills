你是這一場多輪審查的**協調者**，負責判斷和修改。每一輪你都用 orca 開一個新的 Claude Code session 當審查員：它只審、只回報。你逐條查證、決定改什麼、動手改，直到**收斂**：剩下的都是可改可不改的小問題。每多審一輪，就多一次機會加進沒必要的東西，所以審查的目的是確認成品沒有錯；挑問題不是目的。

參數：$ARGUMENTS

審查員用一個全新的 session、不用你自己的子代理，原因有兩個：它要能再開分角度的子代理和盲做；它的上下文要乾淨，沒有前幾輪的東西。

`<O>` 是 `${CLAUDE_PLUGIN_ROOT}/orca`（plugin 根目錄的 `orca/`）。**先讀 `<O>/COORDINATOR.md`**：開工、等待、被叫醒、Heads up、規則、回報都照它，這份只寫審查獨有的部分。

## 開工

1. 照 COORDINATOR.md「開工」，再呼叫 Skill 工具載入 `diff`；`<DIFF>` 是 `${CLAUDE_PLUGIN_ROOT}/skills/diff`，下面提到的 DOCUMENT.md 也在那裡。
2. 讀專案的 CLAUDE.md / AGENTS.md 和要審的產出，找出：
   - 原始檔和輸出檔（例如 `build.py` 產生 docx、`poster.html` 輸出 PDF）。改的是原始檔，而且照專案的規定改。
   - 重建指令，以及怎麼渲染成看得到的形式（PDF 逐頁轉圖、HTML 用瀏覽器自動化工具照實際尺寸截圖）。
   - 唯一依據：題目、評分指引、課件、數據。數據要追到**原始來源**：題目要作者自己找的數據（例如「your time series」），寫原始網站、指標和取得方式。repo 裡處理過的數據檔（檔名帶期間、篩過、合併過）是成品的一部分，不算依據，因為篩掉的部分正是審查要看的。
   - 使用者的偏好：參數、對話、專案文件裡寫的都算，例如「保留小錯誤」「少用逗號」「不看文法」。
   - 已定案：專案筆記裡寫明「不要再改」的決定。每一條補上理由和出處，下一輪的人才能自己核對，並分成兩類：
     - **明文**：本題依據的原文就這樣規定。出處寫本題依據的檔名和頁碼。
     - **讀法**：依據沒寫死、由我們選的做法。出處來自別份作業、別題、小組慣例或「跟之前一致」的，一律是讀法。每條寫出依據原文、其他讀法、各自的後果。讀法只有在使用者**看過原文和其他讀法**後拍板才算定案；紀錄裡只有「照你建議」「選這版當底」這類回覆的，在第 5 步重新問。
3. 產出要在 git 裡，而且那幾個檔案沒有未提交的改動。不在 repo 裡的檔（例如桌面上手改的 docx），先問使用者要放在專案的哪裡，放好再 commit。記下目前分支 `BASE_BR` 和起點 `START=$(git rev-parse HEAD)`，再用 `<DIFF>/scripts/diff.py <起點輸出> <起點輸出> --words`（docx、pdf 要的套件見 DOCUMENT.md）記下起點字數。起點輸出用 `git show $START:<路徑>` 取出來。
4. 照 [`reviewer.md`](reviewer.md) 擬固定部分：要審的東西、依據、偏好、讀者（誰來評這份成品，例如改卷的老師、審稿人、客戶）、角度、盲做幾個（預設 2）。角度照產出的類型挑，每個角度只看一件事，例如：
   - 老師要求與格式
   - 數字重算
   - 逐題有沒有正面回答
   - 版面（逐頁渲染來看）
   - 寫法像不像學生寫的
   - 視覺層次與可讀性（海報）
5. 用 AskUserQuestion 一次問完：COORDINATOR.md〈授權〉、依據清單、偏好、讀者、定案清單（明文和讀法分開列，讀法逐條附原文和其他讀法）、角度、輪數上限（預設 4）、收尾時直接合併回 `BASE_BR` 還是先給使用者看過，附上擬好的 prompt。之後這些段落每一輪都一字不改。
6. 批次目錄 `<scratchpad>/review-<名稱>/`，ledger 放在裡面（格式見〈Ledger〉）。`<名稱>` 用英文 kebab-case，會出現在分支名裡。
7. **開你的 worktree**：`git -C <repo> worktree add -b review/<名稱>/work <批次目錄>/work $START`。之後修改、重建、渲染、commit 都在 `<批次目錄>/work` 裡做，使用者的主目錄從頭到尾保持原樣；重建要的依賴照專案指令在這裡裝一次。

完成條件：第 5 步的每一項使用者都回覆了；`START`、起點字數、固定 prompt 的路徑在 ledger 裡；在 `<批次目錄>/work` 重建一次，渲染出來和起點相同。

## 每一輪

1. **寫 prompt**：寫成 `<批次目錄>/r<N>/prompt.md`，內容是固定部分，加上目前的「已定案」和「這一輪特別看」。
   - 第一輪：「整份從頭審。」
   - 之後每一輪：列出上一輪改過的地方（位置、改成什麼），附上 `git diff <上一輪起點>..<上一輪終點> -- <原始檔>`。寫明：這些地方最容易改錯或說過頭，要逐一確認；其他部分照常審。

   **獨立**：prompt 只放固定部分和這一輪的變動；前幾輪的意見、駁回清單、你對成品的看法都留在 ledger。重複出現的意見由你對照 ledger 擋掉。
2. **開審查 session**：先把要審的版本 commit 好，再 `bash <O>/scripts/open-worktree.sh <repo 選擇器> review-<名稱>-r<N> review/<名稱>/work review/<名稱>/r<N> <批次目錄>/r<N>/prompt.md`。它從你最新的 commit 開一個審查專用的 worktree 和子 session，審查員在那裡渲染、跑腳本，碰不到你的檔。然後照 COORDINATOR.md 掛等待。
3. **被叫醒**：照 COORDINATOR.md「子 session 的一輪」，另外：
   - **提問**：需求類的照依據回答；要它判斷的回「照你的判斷，寫進報告」。成品好不好、前幾輪說了什麼，都留在你這裡。
   - **Heads up**：照 COORDINATOR.md 記下原文、收起，但不轉給審查員：把它當成這一輪多出來的一條意見，跟報告一起進第 4 步查證。只有內容是審查員自己在改檔、做 git 或對外動作時，才馬上叫它停。
   - **做完了**：讀 `r<N>/report.md`。`git -C <審查 worktree> status --short` 有東西或多了 commit，代表它違反只讀：記進 ledger，它改的不會進你的分支。
   - **收掉**：`bash <O>/scripts/close-worktree.sh <repo> <審查 worktree>`：關終端、移除 worktree、刪掉沒有新 commit 的分支。審查員有 commit 時分支會留著，收尾時列給使用者。
4. **查證**：報告的每一條和這一輪的 Heads up 都由你親自查，只用一種方法：數字就重算，引用就打開依據找原文，版面就渲染出來看。引用要查兩件事：原文在，而且那段原文管的是**本題**（同一份題目、同一小題）。別份作業的規定抄得再準，放到這一題也只是讀法。
   - 每一條只有兩種結果：採納（附證據）或駁回（附理由）。
   - 級別由你照 `reviewer.md` 的分級標準重新判，審查員給的級別只是參考。
   - 和 ledger 裡已駁回的意見相同，就引用當時的理由駁回。除非這次帶了新的依據，才重新查。
   - 和明文定案衝突，而且附了反證的：先不要改，問使用者。
   - 報告「讀法」段的每一條，以及盲做和成品讀法不同的地方，由使用者決定：你只核對原文和兩邊的後果（要改哪些數字、表格、結論），在回報裡列給使用者。使用者看過原文後已經拍板的同一條讀法，引用那次決定駁回。
5. **修改**：只改採納的必須修和建議修。
   - 每一條都用能消除問題的最小改動，以刪除和替換優先。要加內容時，先在 ledger 寫明不加的話會錯在哪。
   - 在 `<批次目錄>/work` 改原始檔、重建，再把改到的地方渲染出來看。
   - 在 `review/<名稱>/work` 上 commit，例如 `fix(<scope>): apply review round <N>`，再記下字數。
   - 以下幾種情況先停下來問使用者：要改數字、數據或表格內容；要推翻定案；依據沒有規定、使用者也沒說過偏好的取捨；這次要改的地方，前幾輪已經往相反方向改過（來回擺盪）。
6. **回報**：發一則短訊息。沒有待決的讀法就不必等使用者回覆，直接照第 7 步走：
   - 採納幾條、駁回幾條
   - 改了什麼：位置、改法、依據
   - 駁回的每條一句理由
   - 要使用者決定的讀法：每條附依據原文、目前的讀法、另一種讀法、各自要改什麼。有這一項就等使用者回覆，拍板後記進定案；改了讀法算必須修
   - 字數比起點多或少多少
   - 下一步是再審一輪還是收尾
7. **判斷要不要再審一輪**：這一輪採納了至少一條**必須修**，才開下一輪，因為改錯處的地方需要重新審。
   - 只採納了建議修：改完就收尾。最後的精簡審查會一起把關這些改動。
   - 什麼都沒採納：直接收尾。
   - 到了輪數上限：停下來問使用者。

完成條件：報告的每一條和這一輪的 Heads up，在 ledger 的處置表裡都是採納或駁回；`review/<名稱>/work` 的 `git status` 乾淨；這一輪結束時的字數記了。

## 收尾

1. **精簡審查**：用 Agent 工具開一個子代理，`model: "opus"`，prompt 照 [`final-review.md`](final-review.md) 寫（`{{REPO}}` 填 `<批次目錄>/work`）。
   - 給它起點版和最終版的渲染圖。
   - 給它沒有附說明的比對資料：`<DIFF>/scripts/diff.py <起點輸出> <最終輸出> -o <批次目錄>/plain-diff.json`（不帶 `--notes`；格式寫在 `diff.py` 開頭）。它讀資料比讀頁面準，這一步不做給人看的頁面。
   - 不給它輪次紀錄。

   它的每一條意見照「每一輪」第 4 步查證。查證過的刪減和精簡照做，這一步不加內容，改完重建、渲染、commit。它指出的「改錯」算必須修：修好之後回到「每一輪」開下一輪審查，這一輪特別看那幾處，收斂後再回到這一步。這樣開的輪一樣算進輪數上限。
2. **總 diff**：照 `diff` 的 DOCUMENT.md 做起點輸出對最終輸出，標籤用 `--before-label 起點 --after-label 最終版`。
   - `notes.json`：每一處改動對應哪一輪、哪一條意見、依據是什麼，從 ledger 抄。
   - 頁面另寫三段：不在文字裡的改動（版面、圖、顏色）、中途加過又刪掉的內容、起點和最終版的渲染圖並排。

   輸出到 `<批次目錄>/work` 裡產出旁邊的 `<產出名> 修改對照（起點→最終版）.html`，照 DOCUMENT.md 的檢查確認。
3. **寫回定案**：使用者在這幾輪新拍板的決定，連同理由，寫進專案記錄決定的地方（例如評核資料夾的 README）。和總 diff 放在同一個 commit。
4. **合併**：照開工時問到的做（要先給使用者看，就先發第 5 步的報告、等回覆）。在主目錄跑 `bash <O>/scripts/preflight.sh <repo> <BASE_BR>`，再 `git -C <repo> merge --no-ff review/<名稱>/work -m "merge: review <名稱>"`。主目錄這段時間有了別的 commit 而撞到衝突：`git merge --abort`，問使用者。合併後 `git -C <repo> worktree remove <批次目錄>/work`、`git -C <repo> branch -d review/<名稱>/work`。push 照 COORDINATOR.md「規則」，分支是 `BASE_BR`。
5. **最後報告**：
   - 結論：能不能交
   - 跑了幾輪，每輪採納和駁回各幾條
   - 起點和最終版的字數
   - 剩下的可不修項目
   - 使用者交件前要自己手動做的事
   - 總 diff 的路徑、合併 commit（或還沒合併、在等使用者）、留下的分支
   - 每一輪審查 session 的 session id，可以用 `claude --resume` 回看

完成條件：總 diff 頁首的改動數等於 `diff.json` 的 `counts.groups`；合併 commit 在 `BASE_BR` 上，或最後報告寫明還在等使用者；`git worktree list` 沒有這一場的審查 worktree。

## 規則

審查員只讀不改；修改只由你來做，而且只在 `<批次目錄>/work` 裡做。其餘照 COORDINATOR.md「規則」。

## Ledger

- **頂部「目前」段**（COORDINATOR.md 的共同欄位之外）：`BASE_BR`、`START`、你的 worktree（`<批次目錄>/work`，分支 `review/<名稱>/work`）、收尾要直接合併還是先給使用者看、原始檔與輸出檔、重建指令、渲染指令、輪數上限、固定 prompt 的路徑。
- **「定案」段**：每一條寫決定、類別（明文或讀法）、理由、出處、由誰拍板；讀法再寫使用者拍板時看過的原文和其他讀法。
- **「駁回紀錄」段**：意見摘要 → 理由 → 第幾輪。
- **「字數」表**：起點和每一輪結束時的字數。
- **每一輪一段**：審查 worktree、handle、session id、報告路徑、Heads up 原文、逐條處置表（意見 → 採納或駁回 → 證據或理由 → 改法）、commit、有沒有開下一輪，以及理由。
