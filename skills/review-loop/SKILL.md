你是這一場多輪審查的**協調者**，負責判斷和修改。每一輪你都用 Orca 的 orchestration 開一個新的 worker 當審查員：
它只審、只回報。你逐條查證、決定改什麼、動手改，直到**收斂**為止。

收斂指的是剩下的都是可改可不改的小問題，不是找不到任何問題。每多審一輪，就多一次機會加進沒必要的東西。
所以審查的目的是確認成品沒有錯；挑問題不是目的。

參數：$ARGUMENTS

審查員要用一個全新的 session，而不是你自己的子代理，原因有兩個：它要能再開分角度的子代理和盲做；它的上下文裡
不能有前幾輪的東西。

## 開工

1. 呼叫 Skill 工具兩次，分別載入 `orchestration` 和 `doc-diff`。照 `orchestration` 的指示讀 Orca 附帶的版本對應指南。
2. 讀專案的 CLAUDE.md / AGENTS.md 和要審的產出，找出：
   - 原始檔和輸出檔（例如 `build.py` 產生 docx、`poster.html` 輸出 PDF）。改的是原始檔，而且照專案的規定改。
   - 重建指令，以及怎麼渲染成看得到的形式（PDF 逐頁轉圖、HTML 用 playwright 照實際尺寸截圖）。
   - 唯一依據：題目、評分指引、課件、數據。
   - 使用者的偏好：參數、對話、專案文件裡寫的都算，例如「保留小錯誤」「少用逗號」「不看文法」。
   - 已定案：專案筆記裡寫明「不要再改」的決定。每一條都要補上理由和出處，下一輪的人才能自己核對。
3. 產出要在 git 裡，而且那幾個檔案沒有未提交的改動。不在 repo 裡的檔（例如桌面上手改的 docx），先問使用者
   要放在專案的哪裡，放好再 commit。記下起點 `START=$(git rev-parse HEAD)`，再用
   用 `doc-diff` 腳本的 `--words` 記下起點字數。起點輸出用 `git show $START:<路徑>` 取出來。
4. 照 [`reviewer.md`](reviewer.md) 擬固定部分：要審的東西、依據、偏好、角度、盲做幾個（預設 2）。角度照產出的類型挑，
   每個角度只看一件事，例如：
   - 老師要求與格式
   - 數字重算
   - 逐題有沒有正面回答
   - 版面（逐頁渲染來看）
   - 寫法像不像學生寫的
   - 視覺層次與可讀性（海報）
5. 用 AskUserQuestion 一次問完：依據清單、偏好、定案清單、角度、輪數上限（預設 4），附上擬好的 prompt。
   之後這些段落每一輪都一字不改。
6. 在 scratchpad 建批次目錄 `review-<名稱>/`，放 `ledger.md`（格式見「Ledger」）。你的上下文會被壓縮，
   **每次被叫醒先讀 ledger**。

## 每一輪

1. **寫 prompt**：寫成 `<批次目錄>/r<N>/prompt.md`，內容是固定部分，加上目前的「已定案」和「這一輪特別看」。
   - 第一輪：「整份從頭審。」
   - 之後每一輪：列出上一輪改過的地方（位置、改成什麼），附上 `git diff <上一輪起點>..<上一輪終點> -- <原始檔>`。
     寫明：這些地方最容易改錯或說過頭，要逐一確認；其他部分照常審。

   **獨立**：prompt 裡不放前幾輪的意見、駁回清單，也不放你自己對成品的看法。重複出現的意見由你對照 ledger 擋掉。
2. **開審查 worker**：
   `orca orchestration worker-start --spec-file <批次目錄>/r<N>/prompt.md --worktree current --agent claude --task-title "review round <N>" --json`。
   它和你在同一個 worktree，審的就是你剛 commit 的版本；它工作時你不改檔。把收據裡的 dispatch id 寫進 ledger，
   然後結束回合。Orca 會在它提問或回報時叫醒你；不要輪詢。
3. **被叫醒**：先讀 ledger。
   - 如果它在提問：需求類的問題照依據回答（`orca orchestration reply`）；要它判斷的問題就回「照你的判斷，寫進報告」。
     成品好不好、前幾輪說了什麼，都不告訴它。
   - 如果它停下來但沒回報：照 orchestration 指南處理，用 `send` 叫它從中斷處繼續。
   - 如果它回報做完了：讀 `r<N>/report.md`，再用 `git status` 確認它沒有改到 repo。有改到，就先把改動存成
     `r<N>/stray.patch`，再丟掉，並記進 ledger。做完的 worker 會自己關掉。
4. **查證**：每一條都由你親自查，只用一種方法：數字就重算，引用就打開依據找原文，版面就渲染出來看。
   - 每一條只有兩種結果：採納（附證據）或駁回（附理由）。
   - 級別由你照 `reviewer.md` 的分級標準重新判，審查員給的級別只是參考。
   - 和 ledger 裡已駁回的意見相同，就引用當時的理由駁回。除非這次帶了新的依據，才重新查。
   - 和定案衝突，而且附了反證的：先不要改，問使用者。
5. **修改**：只改採納的必須修和建議修。
   - 每一條都用能消除問題的最小改動，以刪除和替換優先。要加內容時，先在 ledger 寫明不加的話會錯在哪。
   - 改原始檔、重建，再把改到的地方渲染出來看。
   - 在本地 commit，例如 `fix(<scope>): apply review round <N>`，再記下字數。
   - 以下幾種情況先停下來問使用者：要改數字、數據或表格內容；要推翻定案；依據沒有規定、使用者也沒說過偏好的取捨；
     這次要改的地方，前幾輪已經往相反方向改過（來回擺盪）。
6. **回報**：發一則短訊息，不必等使用者回覆：
   - 採納幾條、駁回幾條
   - 改了什麼：位置、改法、依據
   - 駁回的每條一句理由
   - 字數比起點多或少多少
   - 下一步是再審一輪還是收尾
7. **判斷要不要再審一輪**：這一輪採納了至少一條**必須修**，才開下一輪，因為改錯處的地方需要重新審。
   - 只採納了建議修：改完就收尾。最後的精簡審查會一起把關這些改動。
   - 什麼都沒採納：直接收尾。
   - 到了輪數上限：停下來問使用者。

## 收尾

1. **精簡審查**：用 Agent 工具開一個子代理，`model: "opus"`，prompt 照 [`final-review.md`](final-review.md) 寫。
   - 給它起點版和最終版的渲染圖。
   - 給它一份沒有附說明的逐字對照：用 `doc-diff` 產出 `<批次目錄>/plain-diff.html`，不帶 `--notes`。
   - 不給它輪次紀錄。

   它的每一條意見照「每一輪」第 4 步查證。查證過的刪減和精簡照做，這一步不加內容，改完重建、渲染、commit。
   它指出的「改錯」算必須修：修好之後回到「每一輪」開下一輪審查，這一輪特別看那幾處，收斂後再回到這一步。
2. **總 diff**：照 `doc-diff` 的步驟做起點輸出對最終輸出，`notes.json` 這樣寫：
   - `notes`：每一處改動對應哪一輪、哪一條意見、依據是什麼，從 ledger 抄。
   - `other`：不在文字裡的改動，例如版面、圖、顏色。
   - `removed_midway`：中途加過、最後又刪掉的內容。
   - `images`：起點和最終版的渲染圖，逐頁或整張海報並排。

   輸出到 `<產出旁邊>/<產出名> 修改對照（起點→最終版）.html`，標籤用 `--before-label 起點 --after-label 最終版`，
   照 `doc-diff` 的檢查步驟確認。
3. **寫回定案**：使用者在這幾輪新拍板的決定，連同理由，寫進專案記錄決定的地方（例如評核資料夾的 README）。
   和總 diff 放在同一個 commit。push 照使用者的授權。
4. **最後報告**：
   - 結論：能不能交
   - 跑了幾輪，每輪採納和駁回各幾條
   - 起點和最終版的字數
   - 剩下的可不修項目
   - 使用者交件前要自己手動做的事
   - 總 diff 的路徑和 commit
   - 每一輪審查 worker 的 dispatch id（`orca orchestration worker-read` 可以回看）

## 規則

- 只碰自己開的 worker。審查員只讀不改；修改只由你來做。
- 使用者叫你做 X 就只做 X。想順手清的東西另外問。

## Ledger

- **頂部「目前」段**：repo、原始檔與輸出檔、重建指令、渲染指令、`START`、輪數上限、固定 prompt 的路徑。
- **「定案」段**：每一條寫決定、理由、出處、由誰拍板。
- **「駁回紀錄」段**：意見摘要 → 理由 → 第幾輪。
- **「字數」表**：起點和每一輪結束時的字數。
- **每一輪一段**：dispatch id、報告路徑、逐條處置表（意見 → 採納或駁回 → 證據或理由 → 改法）、commit、
  有沒有開下一輪，以及理由。
