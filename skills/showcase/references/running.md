# 跑修改前與修改後

為證據跑任何東西之前讀這份。每一節結尾是相信結果之前必須成立的條件。

## 跑法從哪來

依序找，前一個沒有才往下：

1. repo 的 agent 指令檔（`AGENTS.md`、`CLAUDE.md`，以及子目錄裡的同名檔）與 project skills。之前的 showcase 經使用者同意後，會把跑法寫在這裡。
2. repo 自己記錄怎麼跑的地方，大致由便宜到貴：README、CONTRIBUTING 與開發文件、CI workflow（CI 證明了那些指令能跑）、套件 scripts 與 task runner、e2e 與 Storybook 設定、container 檔案、fixture、seed、mock 與假伺服器。有 e2e 測試的 repo 通常附假後端或種子資料：e2e 設定告訴你怎麼啟動，spec 告訴你怎麼走到每個狀態。
3. 都找不到：問使用者怎麼啟動，不要猜。問的時候列出你看過哪些檔案、試過什麼、卡在哪一步，使用者只需補缺的那一塊。

指令檔寫的和 repo 實際行為不一致時，以 repo 為準，並在交接時把要修正的那行一起提給使用者。

## 執行目錄

每次執行在 repo 外建一個新目錄：有 session 的 scratch 或暫存區就建在裡面，否則用 `mktemp -d`。Windows 的路徑上限是 260 字元，而依賴安裝與建置會長出很深的目錄；scratch 的路徑若已經很長（超過 60 字元左右），改在系統暫存目錄下用短名字建。這次執行所有暫時的東西都放這裡：worktree、輔助腳本、log、原始擷取。平行的執行不會互撞，收尾也只需清一處。

Windows 上在 POSIX shell 裡，傳給 shell 以外程式（node、python、瀏覽器）的路徑要轉成原生格式：`cygpath -m`。

## Checkout

不是「目前工作區」本身的那一邊，都用自己的 checkout 跑：`git worktree add --detach <執行目錄>/<邊> <rev>`。開發者的工作區、分支與 stash 保持原樣。

新的 worktree 沒有安裝好的依賴，也沒有建置產物。用 repo 自己的指令安裝（有 lockfile 通常很快）。如果改用連結共用依賴目錄，移除 worktree 之前先拆掉連結，免得移除動作沿著連結刪到原本那份。

## 出處確認

相信任何輸出之前，證明每一邊跑的是自己那份 checkout 的程式碼。editable install、全域建置、共用的 virtualenv、快取的 bundle，或 port 上早已有一個 server，都會讓「base」默默跑了 head 的程式碼，或反過來。檢查一個兩邊不同的東西：程序 import 進來的模組路徑、server 服務的建置目錄、版本字串，或這次改動本身改到的字串。

完成條件：每一邊都出現一個只可能來自它自己 checkout 的標記。

## 程序

每個常駐程序（server、watcher、模擬器）要能活過單次工具呼叫：用工具的背景模式，或分離式啟動。要留給實機預覽的程序得活到使用者測完，比你這一回合、甚至比你這個 agent 都久：用作業系統層級的分離式啟動（Windows `Start-Process`、POSIX `nohup … &` 或 `setsid`），工具的背景模式可能在回合結束時一併收掉它。記下真正在服務的那個程序的 PID，不是外層包裝：套件執行器的 shim、venv 啟動器與 shell 包裝會藏住它，所以直接啟動程式本身，或從它監聽的 port 反查 PID（Windows 用 `netstat -ano`），沒有 port 的就用命令列比對（Windows 用 `Get-CimInstance Win32_Process`）。Windows 上 Git Bash 的 `$!` 不是 Windows PID。之後只按這些 PID 停止，Windows 用 `taskkill /T /PID` 連同子程序一起收。按程式名稱停止會殺掉使用者其他無關的程序。

## 相同條件

base 與 head 用同樣的輸入資料、視窗大小、語系、主題與時鐘，等動畫結束、網路靜止，游標移到不會觸發 hover 的地方。這樣證據裡的每個差異都來自改動本身。

擷取的操作本身會改狀態：server 端記住的設定、app 存下的資料（加入佇列、開關選項）。兩邊從同樣乾淨的狀態開始，會改狀態的擷取排在最後，或兩邊一起重來。

## 走到某個狀態

把 app 帶到改動影響的每個狀態。repo 的 e2e 輔助程式已經知道怎麼登入、塞資料、點過流程，先借用它們再考慮自己寫步驟。要好幾分鐘才到得了的狀態（排程觸發、長時間工作）值得跑一次；安排好擷取順序，讓自己只經過它一次。

為開發或測試而 commit 進 repo 的假帳密，可以拿來登入本機的 app；repo 沒有現成的假帳號、而本機 app 有初始化或註冊流程時，用它建一個假帳號。這些帳密在交接時直接告訴使用者，此外只留在執行目錄：報告、指令檔與 PR 都不放，跟任何秘密一樣。

## 擷取

- **截圖**框住改動的區域：元素截圖，或帶足夠周邊、讓人找得到位置的裁切矩形。只有「在頁面上的位置」本身是重點時，才另加整頁截圖。讀者要能在報告的顯示寬度下看出差異。
- 兩邊用同一個裁切矩形，即使改動讓元素變高，滑桿也對得齊。
- 用 JPEG 或 WebP，HTML 才不會太大。
- **文字輸出**留下顯示結果的那幾行：摘要行、斷言、改變的值。刪掉 log 雜訊，每處刪減標 `…`。
- **測試當證據**：新增或改動的測試在兩邊都跑，就是 before-after 證據。把 head 的測試檔複製進 base 的 checkout；在那裡失敗（或編譯不過）、在 head 通過，顯示了改動新增的東西。重構的話，base 自己的測試在 base 通過、head 的在 head 通過，顯示行為保持不變。
- **自己寫的重現**：給沒附測試的改動用。放在執行目錄、兩邊都跑，原始碼以不帶 `command` 的 `output` 項目放進報告，說明寫明「為這次 showcase 撰寫，不屬於這次改動」。

## 實機預覽

使用者選了實機預覽時，證據收完後兩邊留著讓使用者親手比對。擷取時改過狀態的那一邊，先用乾淨狀態重啟，使用者看到的才是初始畫面。

使用者接手時，每一邊都已經停在要比對的畫面：需要登入的已經登入，用擷取時走過的同一套步驟帶到改動影響的狀態。使用者第一個動作就是比對，而不是登入或找路。

- **網頁**：base 與 head 各佔一個 port。用你能控制、使用者看得見的瀏覽器視窗打開，例如 repo 或你手上已有的瀏覽器自動化，以有畫面的模式啟動。在視窗裡登入、走到畫面，然後把視窗留著。每一個 server 用自己的瀏覽器 context 或 profile：cookie 只按主機區分，不分 port，所以都在 `127.0.0.1` 上的幾個 server 共用同一份 cookie，登入一邊就會蓋掉另一邊的 session。開著視窗的那支程序也是常駐程序（見〈程序〉），記下它的 PID。
  沒辦法開受控的視窗時，改用使用者的預設瀏覽器打開網址（Windows `start`、macOS `open`、Linux `xdg-open`），並做到以下兩點：
  - 讓每一邊的 cookie 分開：用不同的主機名（例如一邊 `127.0.0.1`、一邊 `localhost`，前提是 server 聽得到該位址），或請使用者把其中一邊開在無痕視窗。
  - 交接時給登入用的帳密。
- **手機或桌面 app**：照 repo 對裝置與模擬器的規矩做（有些裝置上放著不能動的資料或別的版本）。只安裝這次建置出來的東西。要裝到裝置上已經有的 app id 時（會覆蓋它，可能清掉它的資料），repo 的規矩明確允許才裝，否則先問使用者。兩版的 app id 不同時兩版都裝；相同時裝 head，並給使用者切換到 base（以及切回來）的確切指令。需要模擬器而它沒開時，啟動它。裝置上既有的資料比要裝的版本新（例如資料庫 schema 無法降版）時，清資料前先照 repo 規矩，規矩沒寫就問使用者；清之前備份。
- **CLI 或函式庫**：兩個 checkout 留著，給使用者在各自目錄要跑的確切指令。

在交接時列出每一邊在哪裡、怎麼用，以及你記下的 PID。預覽期間 worktree 要留著。

## 收尾

時機：有實機預覽時，使用者說測完了才收；沒有預覽（使用者沒選，或沒有使用者在場）時，證據收完馬上收。

停掉你記下的每個 PID，移除你加的每個 worktree（`git worktree remove`，再 `git worktree prune`）。安裝與 codegen 常把你自己的暫時 worktree 弄髒；在那裡、也只在那裡，可以用 `--force`。從裝置移除你為預覽裝上去、原本不在的 app；覆蓋過的原有 app 無法復原，在交接時已經說過。啟動過的模擬器問使用者要不要關。最後刪掉執行目錄。

完成條件：`git worktree list` 與 `git status` 和開始時一致，你記下的 PID 都已不在，port 都已釋放。
