# 程式改動

讀者沒寫這個改動。頁面替他回答四個問題：做了什麼、為什麼、做了哪些決定、我怎麼親眼看到，不必去問寫它的 agent，也不必自己把程式跑起來。完整 diff 在 PR 的檔案頁已經有了，這頁補 diff 說不出來的部分。

頁面語言：使用者指定的，或長期指示裡設定的；都沒有就跟 repo 的 PR 描述，再來是 repo 文件。

## 1. 範圍

使用者給了 commit、範圍、PR 或分支就照用。沒給時依序找，取第一個存在的，說一句你用哪個：

1. 這個 session 做的改動：從 session 開始時的 HEAD 到現在，含未 commit 的。
2. 未 commit 的工作。
3. 目前分支相對預設分支（`git merge-base HEAD origin/<預設分支>`）。
4. 目前分支的 PR（`gh pr view --json baseRefName,headRefOid`，base 取兩者的 merge-base）。

單一 commit 是 `<commit>^..<commit>`。

完成條件：`git diff --stat <base> [<head>]` 列出的正好是要展示的改動。混進無關的 commit 時，問使用者要展示哪部分。

## 2. 為什麼

讀每一個可能說明意圖的來源：產生改動的對話、PR 描述、commit message、分支名、引用的 issue / 票 / 規格、碰到的 ADR 與設計文件，記下用了哪些。票涵蓋的範圍比這次大時，只拿來解釋為什麼。

完成條件：「為什麼」和每個決定的每一句，不是附了來源，就是標了推斷；沒有任何來源時寫「待作者補充」。

## 3. 證據

按讀者觀察得到什麼來分類改動，一個改動可以屬於好幾類：

| 類型 | 證據 |
|---|---|
| 看得見的 UI | 每個受影響的畫面與狀態，修改前後各截一張 |
| 要操作才看得出的 UI（動畫、轉場、多步流程） | 前後用同一套操作各錄一段 |
| 行為（CLI、API、資料處理） | 同一份輸入跑前後，輸出並排 |
| 效能 | 同一個 benchmark 跑前後 |
| 附測試的修正或新邏輯 | 新測試在修改前失敗、修改後通過 |
| 沒附測試的修正 | 自己寫一支重現，前失敗後通過，原始碼放進頁面並註明是為這頁寫的 |
| 意在保持行為的重構 | 兩邊各自的測試都綠、公開介面沒變 |
| 文件或產出檔 | 照 DOCUMENT.md 另做一頁 |
| 只有設定、依賴、文件原始碼 | 敘述與 diff 本身 |

讀者最想看的主要效果，在**證據階梯**上爬得越高越好：`before-after`（兩邊用同樣方式跑過）→ `after`（只跑了修改後）→ `tests`（一邊的測試輸出）→ `static`（什麼都沒跑）。低於 `before-after` 時寫出具體障礙，例如「這個畫面要登入真實帳號」，讀者靠這一行判斷整頁能信到什麼程度。

動手跑任何東西之前先讀 [RUNNING.md](RUNNING.md)：跑法從哪來、獨立 checkout、證明每一邊跑的是自己的程式碼、擷取、收尾。

- 輸入用假資料。改動本身就關於真實帳號或外部服務時，先問再碰。
- 每項證據的說明寫情境和**看到的差異**，例如「從第 40 筆返回：修改前回到頂端，修改後停在第 40 筆」。
- 輸出是**原文**：可以刪到只剩相關的行（每處標 `…`），可以把 token、金鑰、姓名、email、家目錄換成 `<redacted>`、`<home>`；留下的每一行都是程式印出的原樣。頁面貼到公開 repo 就是公開的。

完成條件：每一類都有證據，或寫明了為什麼停在較低等級。

## 4. 寫頁面

依序：

1. 標題、範圍（base 和 head 的短 SHA，有分支名附上）。
2. **摘要**：1 到 3 句，使用者會感受到什麼改變。寫效果，不寫實作。
3. **為什麼**，附來源。
4. **怎麼做**：白話講主要組成。能用一張最小的圖講清楚就畫：虛擬碼、呼叫樹、檔案樹、只標增減的示意 diff。
5. **合併風險**：單向門還是雙向門（刪資料、改持久化格式、對外介面的破壞性變更、已發出去的東西是單向門；還原 commit 就回得去的是雙向門），和影響範圍（版面、下游消費者、行動版、效能）。
6. **決定**：審查者可能質疑的每個選擇：為什麼、考慮過的替代方案、有來源還是推斷。
7. **證據**：修改前後並排；兩張截圖尺寸相同時加滑桿對照。點圖放大。
8. **關鍵 diff**：撐起這次改動的少數幾段 hunk，各附一句它做什麼、為什麼，縮到關鍵的幾行。
9. **檔案**：每個改動的檔案一行說明；一組同性質的（產生的程式碼、lockfile、機械式改名）可以合成一行。
10. **親自試**：從乾淨的 checkout 出發、用假資料看到改動的步驟。
11. **沒驗證到的**：平台、流程、邊界情況。

hunk 和證據輸出由程式填進頁面：把 `git diff <base> <head> -- <檔>` 和指令輸出存成檔，頁面放 `<script type="application/json" id="data">__DATA__</script>` 和讀它的 JS，再

```
python <skill 目錄>/scripts/fill.py page-src.html -o <輸出.html> --text hunk_a=a.diff --text tests_before=before.txt …
```

（截圖和錄影用相對路徑寫在 `<img>` / `<video>` 裡，會一起內嵌。）交出前用 `grep` 掃一次頁面和證據文字有沒有家目錄路徑、像金鑰的字串。

完成條件：讀者只看摘要、為什麼、親自試，就答得出「改了什麼、為什麼、我怎麼看到」。

## 5. 交付之後

- 用預設瀏覽器打開頁面（macOS `open`、Windows `start`、Linux `xdg-open`）。
- 使用者要貼到 PR：另寫一份純文字 Markdown（圖改成說明文字），問過再用 `gh pr comment <編號> --body-file`。`gh` 傳不了 HTML，要在 PR 上看到圖，請使用者在網頁把 HTML 檔拖進留言框。
- 這次自己找出或問來的跑法（指令、陷阱、出處確認方式），repo 的指令檔沒寫的：把打算寫的文字給使用者看，同意才寫進 repo 的 `AGENTS.md` 或 `CLAUDE.md`。
