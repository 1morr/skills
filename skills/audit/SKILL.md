使用者是這些文件的作者，要知道哪裡該改，並在動手前核可每一項。這個 session 停兩次等他：交出**發現**、**執行**完。

參數：$ARGUMENTS

標準是 mattpocock 的寫法：呼叫 Skill 工具載入 `mattpocock-skills:writing-for-agents`，範圍裡有 skill 時連它的 `SKILL-MECHANICS.md` 一起讀；沒裝這個 plugin 就請使用者先裝。每條發現對到它的一個詞彙。

## 1. 範圍

1. 把參數對成檔案清單：每個 skill 的 `SKILL.md`、附屬 md、md 指到的腳本和範本、它們共用的檔；參數點名指令檔（`AGENTS.md` / `CLAUDE.md`）時，是它和它指到的文件。
2. 讀這些檔所在 repo 的指令檔和檢查（測試、lint、CI）：那個 repo 自己的規則優先於通用標準，已經有檢查守著的規則不再查。
3. 參數給了**對照組**（用過這個 skill 的專案、它的產出、對話紀錄）就列入：它驗文件寫的和實際發生的對不對得上。
4. md 是審查的對象，自己整份讀完。腳本、範本、測試只用來核對 md 說的對不對：超過約 30 個檔時分給子代理（`model: "sonnet"`），要它列出 md 引用的參數、輸出、名稱和實際不同的地方，附兩邊的 `檔案:行號`；疑點由你回原檔查證後才算發現。

完成條件：清單上每份 md 你都讀過，其餘的檔你或子代理讀過。

## 2. 發現

這一段只讀。先直接回答參數裡問的事，再列發現。每條寫成 `檔案:行號` → 現在的寫法 → 問題（對應哪個詞彙）→ 改法，分三類，各自照你打算動手的順序排：

- **純改寫**：執行者的行為不變。
- **改行為**。
- **要使用者決定**：改名、刪除、合併 skill 或改叫用方式；有兩種合理做法的；理由查不清的。每題附建議。

已經夠好、不建議動的也列出來，各附一句原因。

- 建議刪掉一條告誡或已知行為之前，用 `git log -S` / `git blame` 查它當初為什麼加。理由已經消失的附那個 commit；查不到理由的、檔案不在 git 裡的，歸到「要使用者決定」。
- 建議改 repo 的規則時，同一條寫出要補或要刪的檢查，以及會紅和不該紅的例子各一個。
- 有對照組時，每條註明它在對照組裡實際發生過，還是讀文字推斷的；沒有對照組就在開頭說明全部是推斷。

一個畫面放得下就寫在對話；放不下就寫成 scratchpad 的一份 md，在對話給完整路徑、最值得做的幾件事、「要使用者決定」的每一題和建議。每個 skill 現在怎麼跑、各 skill 做法的對照，使用者問到才寫。

完成條件：參數裡問的事都答了；每條發現都有 `檔案:行號` 和分類；`git status` 沒有改動。交出後停下，等使用者回答。

## 3. 執行

照使用者的回答和發現的順序做，每步一個 commit（照那個 repo 的 commit 慣例）。新增檢查的那一步排最前面，後面的步驟才有東西守著。

- 搬動文字的步驟，commit 前確認搬走的每一段在新位置找得到。
- 不在 git 裡的檔：動手前複製一份到 scratchpad，告訴使用者路徑。

完成條件：每條發現不是 commit 了，就是列為「沒做」並寫了原因；那個 repo 的全部檢查在最後一個 commit 上通過；對話裡有 commit 清單、和發現不同的地方、還沒 push 的 commit 數（`git log @{u}..` 算出來的）。
