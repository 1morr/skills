使用者是這些 skill 的作者，要知道它們現在實際怎麼跑、哪裡該改，並且在動手前核可每一項。這個 session 在三個地方停下來等他：交出**報告**、交出**計劃**、**執行**完。

參數：$ARGUMENTS

標準是 mattpocock 的寫法：呼叫 Skill 工具載入 `mattpocock-skills:writing-for-agents`，範圍裡有 skill 時連它的 `SKILL-MECHANICS.md` 一起讀。判斷時用它的詞彙，每條發現對到其中一個。

## 1. 範圍

1. 把參數對成檔案清單：每個 skill 的 `SKILL.md`、附屬 md、md 指到的腳本和範本，加上它們共用的檔。
2. 讀 repo 的指令檔（`AGENTS.md` / `CLAUDE.md`）和它的檢查（測試、lint、CI），分清哪些規則已經由檢查強制、哪些靠自查。
3. 參數給了**對照組**（實際用過這個 skill 的專案、它的產出、過去的對話紀錄）就一併列入：它用來驗 skill 寫的和實際發生的對不對得上。
4. md 是審查的對象：自己用 Read 整份讀完，一次平行讀幾個。腳本、範本、測試只用來核對 md 說的對不對：超過約 30 個檔時分給子代理（`model: "sonnet"`），要它列出 md 引用的參數、輸出、名稱和實際不同的地方，附兩邊的 `檔案:行號`；疑點由你回原檔查證後才算發現。

完成條件：清單上每份 md 你都讀過，其餘的檔你或子代理讀過；每條規則標了「檢查強制」或「自查」。

## 2. 報告

這一段只讀。報告寫成一份 md 放在 scratchpad。

開頭是結論：最值得做的事，最多 5 件，依效益排序；已經夠好、不值得再改的也寫出來。接著：

1. **現狀**：每個 skill 一段，寫步驟、分支、呼叫的腳本、載入的共用檔、完成條件。使用者不開檔案也看得懂它怎麼跑。
2. **一致性**：同一件事在不同 skill 裡的做法並排成一張表（frontmatter 和 description、路徑寫法、步驟與完成條件的格式、子代理和模型的指定、交付方式、共用檔的用法），標出哪一種當標準。
3. **發現**，每條寫成：`檔案:行號` → 現在的寫法 → 問題（對應哪個詞彙）→ 建議的改法。分三類：
   - **純改寫**：執行者的行為不變。
   - **改行為**。
   - **要使用者決定**：改名、刪除、合併 skill 或改叫用方式；有兩種合理做法的；理由查不清的。每題附建議。
4. **行數**：每個檔改前和預估改後。
5. **實作順序**：分幾步，每步改完 repo 的檢查都要能過。

三條規矩：

- 建議刪掉一條告誡或已知行為之前，用 `git log` / `git blame` 查它當初為什麼加。理由已經消失的，附那個 commit 歸到可刪；查不到理由的歸到「要使用者決定」。
- 建議改指令檔的規則時，同一條寫出要補的檢查，以及會紅和不該紅的例子各一個。
- 有對照組時，每條發現註明它在對照組裡實際發生過，或只是讀文字推斷的。

在對話給報告的完整路徑、最值得做的那幾件事、「要使用者決定」的每一題和你的建議。

完成條件：範圍裡每個 skill 在〈現狀〉都有一段；每條發現都有 `檔案:行號` 和分類；`git status` 沒有改動。交出後停下，等使用者回答。

## 3. 計劃

使用者回答之後，寫一份短計劃（同樣放 scratchpad）：

- 每一題照他的回答定案。
- 步驟：每步一個 commit，寫出改哪些檔、跑哪些檢查。新增檢查的那一步排最前面，後面的步驟才有東西守著。
- 界線：哪些東西不動；commit 在哪個分支；push 等他開口。

完成條件：報告的每條發現都落在某一步，或列在「不做」並寫了原因。交出後停下，等使用者確認。

## 4. 執行

照計劃一步一步做：改 → 跑那一步的檢查 → commit（照 repo 的 commit 慣例）→ 下一步，全部做完才回報。

- 搬動文字的步驟，commit 前確認搬走的每一段在新位置找得到。
- 遇到計劃沒涵蓋的取捨就停下來問。
- skill 新增、改名、刪除或改了叫用方式時，repo 列出 skill 的地方（README、manifest）同一步改。

完成條件：計劃的每一步都 commit 了；repo 的全部檢查在最後一個 commit 上通過；對話裡有 commit 清單、行數的預估對照實際、和計劃不同的地方、還沒 push 的 commit 數（`git log @{u}..` 算出來的）。
