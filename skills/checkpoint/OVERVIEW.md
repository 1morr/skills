# 導覽的寫法

讀者是 repo 的主人，不一定懂這個領域，也記不住細節。導覽讓他隔幾週回來，十分鐘內想起：這個程式在做什麼、怎麼運作、某個功能的原理、改哪裡會動到什麼、哪些是他自己定的。

導覽是**地圖**：講原理、畫圖、指路。細節（參數、規則全文、資料格式、API）留在原文件和程式碼，導覽連過去。兩邊都寫細節，遲早互相矛盾；有衝突時以原文件和程式碼為準。

## 檔案

```
docs/overview/
├── README.md          總覽
├── features/<功能>.md
└── decisions.md       決定清單
```

repo 放文件的地方不叫 `docs/` 就照它的慣例。

### README.md

1. 頁首註解 `<!-- checkpoint: <完整 commit sha> <里程碑或日期> -->`：下次 checkpoint 從這裡算範圍。
2. **一段話**：這個程式替誰、做什麼。
3. **核心原理**：3–6 點，每點一個讀者要懂的概念，白話講它怎麼做到（例如「硬連結讓同一個檔案出現在兩個資料夾，卻只佔一份空間」）。
4. **架構圖**：主要元件、外部服務、資料流向。
5. **主要流程圖**：使用者最常走的一兩條路，從觸發到結果。
6. **功能索引**：表格，一個功能一列：名稱（連到 features/）、一句話、狀態（已完成 / 進行中的里程碑 / 計畫中）。
7. **改這裡會動到什麼**：模組或目錄一列：負責什麼、誰依賴它、改了要跑哪些檢查。
8. **已知限制和脆弱處**，附來源。
9. **里程碑紀錄**：每次 checkpoint 一列：里程碑、日期、一句話。

### features/<功能>.md

使用者看得到、叫得出名字的功能一份，檔名和標題用 repo 名詞表的詞。依序：

1. 用途：使用者看到什麼、能做什麼。
2. 怎麼運作：原理和機制。
3. 流程圖。
4. 涉及的模組（路徑）。
5. 相關決定（連到 decisions.md 的列）。
6. 限制。
7. 細節在哪：原文件章節、主要程式檔。

### decisions.md

只收會改變系統怎麼運作、或使用者看到什麼的決定；實作細節的取捨留在票和 commit 裡。表格欄位：日期、決定（一句）、決定者、來源（ADR、文件章節、commit）、使用者看過。

決定者三種：**使用者定**、**使用者同意**（agent 提議）、**Agent 定**。舊決定查不到是誰定的寫「不明」。「Agent 定」在 checkpoint 對話裡給使用者看過後，最後一欄填日期。

## 寫法

- 每節第一句就是重點，先講是什麼、為什麼，再講怎麼做。
- 用名詞表的詞。術語第一次出現就用一句白話解釋。
- 關於機制的句子附來源（`src/x/y.py`、`plan §4.5`）；推斷標「推斷」。
- README ≤ 250 行，每份 feature ≤ 120 行。超過就是抄了細節，改成連結。

## Mermaid

- 用 GitHub 會畫的圖：`flowchart`、`sequenceDiagram`、`stateDiagram-v2`。
- 一張圖 ≤ 15 個節點，多了就拆成總圖加分圖。
- 節點文字一律加引號，中文、括號、斜線才不會壞：`A["下載完成"]`。
- 節點用名詞表的詞和實際的模組名，讀者對得到程式碼。
- 每張圖下面 2–4 句，照箭頭順序講一遍。
- 寫完逐張驗證：在 playwright 打開的回顧頁裡，對每個區塊跑 `await mermaid.parse(code)`，全部通過才算完成。

## 第一次建立

1. 從名詞表、架構文件、ADR、計畫起步，列出功能清單和模組清單。
2. 功能分給子代理，各自讀文件和程式碼，照上面的格式寫 feature 檔草稿，每句附來源。
3. README 和兩張總圖你自己寫，名稱和 feature 檔一致。
4. decisions.md 從 ADR 和偏差紀錄收。

完成條件：功能索引的每一列都有 feature 檔；「改這裡會動到什麼」涵蓋程式碼的每個頂層模組。

## 增量更新

1. `git diff --stat <頁首 sha>..HEAD`，加上第 2 步的回顧。
2. 找受影響的節：新功能加 feature 檔和索引列；機制變了改那份 feature 和它的圖；模組或依賴變了改「改這裡會動到什麼」；新決定進 decisions.md；新限制進「已知限制」。
3. 沒受影響的節維持原文。
4. 抽查**漂移**：挑 3 份這段沒碰的 feature，對照現在的程式碼，說明不對就改，並列在回顧頁。
