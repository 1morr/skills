使用者是 repo 的主人，但常常不是這個領域的專家，很多做法是照 agent 的建議走的。這個 session 讓他重新**看懂**這個程式：剛做完的一段做了什麼、為什麼、接下來要做什麼；他在對話裡定下的事留在文件裡，不只留在這段對話。

參數：$ARGUMENTS

產出三樣：

- **導覽**：repo 裡的 `docs/overview/`，Markdown 加 Mermaid，長期維護、每次增量更新。寫法見 [OVERVIEW.md](OVERVIEW.md)。
- **回顧頁**：這一次的 HTML，放 scratchpad。
- **寫回**：對話定下的事，寫進 repo 記錄決定的地方。

每一句「做了什麼、為什麼、怎麼運作」都附**來源**（`檔案:行`、文件章節、commit、票）；找不到來源的標「推斷」。讀者靠這些句子理解系統，一句錯的說明比沒寫更糟。

## 1. 範圍與來源

1. 讀 CLAUDE.md / AGENTS.md，找出這個 repo 的計畫、進度、票、決定紀錄（ADR、偏差紀錄）、名詞表放在哪裡，以及 session 結尾的規定。
2. 定範圍：
   - 參數是里程碑：它的 spec、票、進度紀錄（含封存檔）；commit 範圍從它第一個 commit 的前一個到驗收 commit。
   - 參數是 commit 範圍：照用。
   - 沒給：`docs/overview/README.md` 頁首記的 commit 到 HEAD；沒有導覽就問使用者。
3. 找**下一段**：計畫裡排在後面的里程碑（已開工就讀它的 spec 和票），或使用者說要做的事。

完成條件：`git log --oneline <範圍>` 列出的正好是這一段；回顧和下一段要讀的文件列成清單。

## 2. 回顧

範圍大就分給子代理，每個帶回附來源的摘要。逐項寫：

- **做了什麼**：照使用者感受得到的效果分組（功能、行為、介面），一組一句「以前…，現在…」。
- **為什麼**：引 spec、票、決定紀錄的原文。
- **對不對**：spec 的驗收逐條對到證據（測試、驗收紀錄、截圖）；列出計畫有但沒做的、做了計畫外的、推翻計畫的。挑這段的關鍵機制，對照現在的程式碼，文件說的和程式做的不一樣就列出來。
- **遺留**：沒過的驗收、使用者接受的未達標、延後的項目、沒處理的 review 發現、新加的 TODO。每項寫**誰接手**（票、里程碑）；沒有就標「沒人接」。
- **決定**：這段時間的決定，每條標**決定者**：使用者定、使用者同意（agent 提議）、Agent 定。

完成條件：每張票、每條驗收、每項遺留都歸了位；「沒人接」和「Agent 定」另外列出。

## 3. 下一段

- 要做什麼、為什麼現在做（引計畫原文）、打算怎麼拆、會碰到哪些現有模組。
- 風險和沒定的事：計畫裡有兩種讀法的地方、依賴卻沒查證的外部事實、和第 2 步的遺留撞到的地方。

## 4. 更新導覽

照 [OVERVIEW.md](OVERVIEW.md)：第一次從程式碼和文件建整份，之後只改這段碰到的部分。

## 5. 回顧頁

寫一頁 HTML 放 scratchpad，用預設瀏覽器打開（macOS `open`、Windows `start`、Linux `xdg-open`）。依序：

1. **要你確認的事**：一題一行，附你的建議和理由。
2. 做了什麼、為什麼，附這段改動後的架構圖或流程圖。
3. 對不對：偏差、文件和程式對不上的地方。
4. 遺留，「沒人接」排最前面。
5. 決定，「Agent 定」排最前面。
6. 下一段的打算和風險。
7. 導覽這次改了哪幾節（連到檔案）。

圖用 Mermaid：圖寫在 `<pre class="mermaid">` 裡，頁尾載入

```html
<script type="module">
  import mermaid from "https://cdn.jsdelivr.net/npm/mermaid@11/dist/mermaid.esm.min.mjs";
  mermaid.initialize({ startOnLoad: true, theme: matchMedia("(prefers-color-scheme: dark)").matches ? "dark" : "neutral" });
</script>
```

外觀照 [`../diff/LOOK.md`](../diff/LOOK.md) 的〈Token〉和〈字體〉，版面是一般文章：70ch 文字欄、標題和留白分段。用 playwright 打開，確認每張圖都畫出來、沒有 `Syntax error`。

## 6. 對話

在對話裡貼「要你確認的事」（一題一行，同回顧頁）和回顧頁的完整路徑，然後回答使用者的問題：

- 回答附來源。問到導覽沒講清楚的地方，答完補進導覽。
- 使用者定了新決定或改了主意：記下，第 7 步寫回。
- 問一次要不要做**理解檢查**：出 2–3 題「如果 X 發生，系統會怎樣」，答不出的地方補進導覽。

使用者說可以了才往下。

## 7. 寫回

1. 對話定下的決定寫進 repo 記錄決定的地方（照 CLAUDE.md：ADR、計畫、需求文件、偏差紀錄），標決定者。
2. 更新導覽的 `decisions.md`（使用者這次看過的「Agent 定」填上日期）、里程碑紀錄、頁首 commit。
3. 照 repo 的規定 commit；有進度紀錄就加一列。
4. 照 repo 的 session 結尾規定給下一步的指令，通常是下一段的開工指令。
