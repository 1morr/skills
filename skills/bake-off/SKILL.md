disable-model-invocation: true
argument-hint: "[版數，預設 3；0 = 只比較現成版本] <任務 prompt 或 prompt 檔路徑> [現成版本的路徑或連結…]"

你是這一場 bake-off 的協調者，自己不做任何一版：每一版從同一個乾淨的起點、拿同一份 prompt 獨立做完，再由你逐版審查，給使用者一份「選哪一版、怎麼改」的報告。

參數：$ARGUMENTS

`<O>` 是 `${CLAUDE_PLUGIN_ROOT}/orca`。**先讀 `<O>/COORDINATOR.md`**，這份只寫 bake-off 獨有的部分。

**獨立**是這個 skill 的核心：每一版只收到共同 prompt、給它自己計畫的意見、和所有版本都一樣的答案。任何一版的內容、做法、評語都只留在那一版，比的才是 N 個獨立的版本。

## 開工

1. 照 COORDINATOR.md「開工」。
2. 讀 prompt（參數是檔案路徑就讀檔）和專案的 CLAUDE.md / AGENTS.md，找出：任務的來源（題目、評分指引、需求文件）、現有的舊產出。任務要自己找的數據，來源寫**原始來源**（網站、指標、取得方式）；repo 裡處理過的數據檔（檔名帶期間、篩過的）算舊產出，因為它帶著上一次的讀法。
   - **外部版本**：使用者附上的現成版本（檔案、資料夾、zip、claude.ai artifact 連結）不開 session，審查時和其他版一起渲染、打分。zip 解到 `<批次目錄>/external/<名稱>/`；artifact 用 `read_artifact` 讀出存成檔。
   - **使用者的偏好**（例如「我覺得 X 比較簡潔順眼」）記進 ledger，報告裡要正面回應。
3. 擬**清除清單**：
   - 刪：舊產出本身和它的輸出檔（PDF、截圖、build 產物）。
   - 改：混在一起的檔。任務原文留著，描述舊產出的段落刪掉；這些段落裡屬於任務的限制（規定、格式、已知的工具地雷）搬進 prompt。
   - 留：任務來源，以及與舊產出無關的東西。
4. 審 prompt，提出修改建議並附理由：產出的形式和位置、什麼算完成、從清除清單搬來的限制、跟「從零做」衝突的字眼（例如「改進現有的」）。沒有建議就直說。prompt 和任務來源裡有兩種**讀法**的地方（例如數據範圍）另外列出附原文；預設讓各版各自讀，各版怎麼讀本身就是比較的結果，使用者要定死就寫進 prompt。
5. 用 AskUserQuestion 一次問完：版數、清除清單、prompt 修改（原樣 / 採用建議）、COORDINATOR.md〈授權〉。
6. 批次目錄 `<scratchpad>/bake-off-<任務名>/`（任務名用英文 kebab-case，會出現在分支名裡），ledger 放在裡面。

版數 0（只比現成版本）：第 3、4 步不做，第 5 步只問授權；建好批次目錄和 ledger 後直接到〈審查〉。

完成條件：第 5 步的每一項使用者都回覆了；批次目錄和 ledger 建好了。

## 起點

1. 從主分支開 base 分支，在臨時 worktree 裡清理，主目錄保持原樣：`git -C <repo> worktree add -b bake/<任務名>/base <批次目錄>/base <主分支>`，照清除清單刪改，`git add` 只點名清單上的檔，commit（例如 `chore(<scope>): clear <產出> for a fresh redo`），再 `git -C <repo> worktree remove <批次目錄>/base`。清單是空的就 `git -C <repo> branch bake/<任務名>/base <主分支>`。
2. 照 [`frame.md`](frame.md) 寫 `<批次目錄>/prompt.md`，`{{TASK_PROMPT}}` 放使用者確認過的 prompt 原文。

完成條件：`git show --stat bake/<任務名>/base` 列出的檔和清除清單一致；`prompt.md` 裡沒有剩下的 `{{`。

## 開版

每一版一行呼叫一次：`bash <O>/scripts/open-worktree.sh <repo 選擇器> <任務名>-<版號> bake/<任務名>/base bake/<任務名>/<版號> <批次目錄>/prompt.md`。每一版各掛一個等待。

完成條件：每一版都印了 `started: yes`，ledger 有它的 worktree、分支、handle、jsonl。

## 計畫關卡

1. 每一版交計畫後會停下。全部交齊再一起處理。
2. 逐版標出問題：取材碰到舊版或歷史、漏了任務的要求、產出沒辦法直接看。各版讀法不同的地方另標「讀法」，只記下來，留給比較。
3. 給使用者一張對照表（版、要讀的檔、做法、產出形式、你的標註），再用 AskUserQuestion 問一次：全部照計畫做 / 照標註修正後做 / 使用者自己寫意見。
4. 每一版各送一則「計畫核可，開始做。」，後面接著**只屬於這一版的**修正。

完成條件：每一版都收到了核可訊息，給它的修正記在 ledger 那一版的段落。

## 進行中

照 COORDINATOR.md「子 session 的一輪」，另外：

- **提問**：任務來源原文有明確答案的，照原文回答並附原文；同一題每一版給同一個答案，第一次回答就記進 ledger 的「共同答案」，之後照抄。設計上的取捨和原文有兩種讀法的問題，回「你自己判斷，寫進最後的回報」，選項題選它推薦的。各版的讀法記進 ledger。
- **Heads up** 的原文只貼給出現它的那一版。
- **說做完了**：分支上有 base 之後的新 commit（`git -C <worktree> log --oneline bake/<任務名>/base..HEAD`）、`git status` 乾淨、最後一則訊息列出的產出檔都在而且可以直接看。缺一項就叫同一個 session 補。

完成條件：每一版都過了「說做完了」那三項。

## 審查

全部版本驗收完才開始。審的是使用者實際會看到的樣子。

1. **先定評分項，再看產出**：從任務來源列出評分項寫進 ledger，在看任何一版之前完成，免得看完再替偏好的那版找理由。
2. **渲染**每一版：PDF 轉逐頁圖、HTML 用瀏覽器自動化工具照實際尺寸截圖、程式實際跑起來；全圖和局部放大，存到 `<批次目錄>/review/<版號>/`。
3. **逐項打分**：每個評分項、每一版給「做到 / 有問題」，有問題的附位置。
4. **讀法對照**：各版讀法不同的地方列成表：原文（檔名、頁碼）、每一版選了什麼和理由、照每種讀法要改哪些內容。你只核對原文和後果，選哪種交給使用者；「和舊作業一致」「小組慣例」這類理由照列，標明出處不是本題的依據。
5. **選基礎版**：選結構和根本做法最好的那一版，也就是事後最難改的部分；細節和潤飾可以從別版搬。讀法不算進選版。
6. **列可合進來的項目**：只列比基礎版好的部分，每項寫來源（版號、檔案:位置）、好在哪裡、搬進來會撞到什麼。

完成條件：每個評分項、每一版都有「做到」或「有問題」，每個「有問題」指得出位置和截圖；讀法對照表每一列都附原文；選基礎版的理由每一條都對得回評分項。

## 報告

先照 COORDINATOR.md〈回報〉送一則短訊息，**要你決定的讀法**：每條一個獨立的問題，和選版分開問；沒有就寫「各版讀法一致」。再一則訊息，依序：

1. **產出位置**：版號、worktree、分支、主要產出檔、`review/<版號>/` 截圖目錄；外部版本列原始位置。
2. **建議的基礎版**，對照評分項說明；使用者說過偏好的，明確寫同不同意、依據哪幾項。
3. **基礎版還要改的地方**：位置和改法；基礎版的讀法和使用者選的不同時列在這裡。
4. **可以從別版合進來的**：來源、內容、理由。
5. 每一版一句話的總評。
6. 下一步：合併之後可以用 `/1morr:review-loop` 一輪一輪審到可以交。

報告到這裡就停，等使用者指示。使用者只回了選哪一版時，先用 AskUserQuestion 逐條問讀法（附原文）。

完成條件：使用者選了版，每條讀法都有他的答案。

## 收尾（使用者指示後才做）

- **合併選定版**：要改的和要搬進來的交給基礎版的子 session 做。比較已經結束，訊息裡明說「這一步可以讀下列其他 worktree 的檔案」，每項附來源的絕對路徑和位置。驗收它的 commit 後，在主目錄跑 `bash <O>/scripts/preflight.sh <repo> <主分支>`，再 `git merge --no-ff bake/<任務名>/<版號>`（base 的清除 commit 一起進來，舊產出正好被取代）。push 照 COORDINATOR.md「規則」。選的是外部版本時，由你把它放到產出原本的位置、改好、commit。
- **寫回讀法**：使用者拍板的讀法連同原文、其他讀法、拍板的回覆，寫進專案記錄決定的地方（例如評核資料夾的 README），和合併同一個 commit。之後 review-loop 會把它當成定案。
- **清 worktree**：每一版跑 `bash <O>/scripts/close-worktree.sh <repo> <worktree>`。沒合併的分支會留著，列給使用者決定要不要刪。

完成條件：`git worktree list` 沒有這一批的 worktree；使用者要合併的，合併 commit 在主分支上；留下的分支都列給了使用者。

## Ledger

「目前」段（COORDINATOR.md 的共同欄位之外）：任務名、版數、base commit、清除清單、prompt.md 路徑。「評分項」、「共同答案」（題目 → 答案 → 依據原文）、「讀法」（原文 → 每一版的讀法和理由 → 使用者的決定）。每一版一段：worktree、分支、handle、session id、狀態（planning / working / done / blocked）、計畫摘要與給它的修正、代答、Heads up 的處置、最後的 commit。
